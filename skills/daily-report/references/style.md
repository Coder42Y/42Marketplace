# 日报的语言、长度和粒度

这份规范来自一份用户认可了长度、粒度和语法的真实日报。骨架见 `assets/skeleton.html`；`references/` 下如果有 `example-*.html`，那就是那份报告。

## 读者和用法

- 读者是例会上的同事，技术背景有深有浅。报告要能直接念出来，念完大约 3 到 5 分钟；有人追问时，往下看「技术说明」能答上来。
- 所以每一项都写两层：
  - **白话层**：正文段落，2 到 4 句。讲清楚发生了什么、为什么要做、现在是什么状态。不懂代码的人也要听得懂。
  - **技术说明层**：放在 `.tech` 块里，左边一条竖线，小标题写「技术说明」或「验证」。条目要具体，能对上代码和 PR。

## 白话层怎么写

- 第一次提到概念时先讲它做什么，不直接甩内部名词。例如：
  - ❌ 订单服务接入事件总线，M2 完成
  - ✅ 下单、支付、发货这几步现在都会发一条记录，后面的对账和通知直接读这些记录，不用再各自去查数据库
  - ❌ 修复 SSRF
  - ✅ 生成链接预览时，服务器会去打开用户贴的链接。原来没有限制访问哪里，一条跳转就可能让服务器去访问内网或云平台的凭证地址。现在每一次跳转都先检查，只允许访问公网地址。
- 内部代号（M1/M2、X-01、D1、Q4 这类）不出现在白话层。要提，就用它的意思代替，比如「准备 / 接入 / 上线」。
- 有意外发现或者纠正了之前的说法，照实写一句。例如：「顺带发现，这个功能上线以来其实一次都没真正发出过请求」。
- 状态用准确的词，每个都有确切含义，不要混用：
  - 已合入：合进主分支了
  - 已开 PR：PR 开了，还没合
  - 已修，待开 PR：本地提交了，还没推送
  - 进行中
  - 等某某：被别的事卡住了

## 技术说明层写什么

具体到这种程度就够了：

- 模块、文件、函数、工具、开关的名字，用 `<code>` 包起来。例如：`services/billing/reconcile.py`、`submit_order`、`event_bus_enabled` 开关。
- 根因要写到机制那一层。例如：「`_NoRedirectHandler` 没有继承 `BaseHandler`，所以 `build_opener` 每次都抛 `TypeError`」，不要只写「修了一个 bug」。
- 设计上的决定，以及为什么这样定。例如：「为什么不在前端修：前端拿到的 ID 本身是对的，精度是在网关把 JSON 解码成浮点数时丢的」。
- 影响范围：哪些地方受影响，哪些明确不受影响。例如：「只对走新网关的请求生效，老的批处理任务不受影响」。
- 验证用的数字：新增了几个测试、回归通过几个、失败几个，失败的是不是主分支上本来就有的；实跑用的模型、样本、耗时、token。
- 子 agent 审查发现了什么、怎么修的，挑一两条有代表性的写。

不写：代码片段、完整 schema、逐字段的长表。

## 去掉 AI 腔（按 humanizer 的规则，换成中文的写法）

- 不用这些词：赋能、闭环、抓手、打通、全面提升、显著、极大地、无缝、深度（作形容词）、助力、持续推进、进一步优化、关键（作形容词，能删就删）。
- 不用「不是 X，而是 Y」「不仅……更……」这类先否定再立论的句式，直接说它是什么。
- 不凑三连排比，不在段尾加总结拔高的句子（比如「为后续……奠定了基础」）。
- 不夸大成果：只跑通一个样本，就写「跑通一个样本，结论正确」，不写「验证了方案的有效性」。
- 破折号少用，能用逗号或句号就不用。
- 句子长短交替。主干用中文；英文术语（PR、token、middleware、schema、worktree）用英文顺手就直接用，不加括号解释。
- 写完通读一遍，看着像发布会稿或者周报模板的句子，就改成平常说话的样子。

## 长度参考（标杆那一版）

- 5 段：开场一句话 / 做完了 / 进行中 / 需要协调·风险 / 明天。「做完了」可以拆成「主线」和「顺手修的问题」两个 h2。
- 主线一项：白话 1 段，1 张机制示意图，1 条步骤条，2 到 5 个技术说明块，1 张数据图或表（有数字的话）。
- 次要的一项：白话 1 到 2 句，加 1 个技术说明块，4 到 7 条。只是关 issue 这类小事，就写一句白话，不加技术说明。
- 进行中：3 条白话，1 张任务状态表（任务 / 做什么 / 状态），1 个技术说明块。
- 需要协调 / 风险：2 到 4 条，每条加粗开头，后面接一两句。
- 明天：3 到 5 条，每条是一个具体动作。
- 整页桌面高度大约 7000 到 9000 px。明显更短，说明粒度太粗；明显更长，说明把过程流水账也写进去了。

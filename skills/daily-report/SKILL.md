# daily-report

把一天的 session 变成一份能在例会上直接念、被追问时能答上来的汇报。交付物是一个单文件 HTML，直接发给用户。

下面提到的路径都相对本 skill 的目录（调用时给出的 base directory）。

- **骨架**：`assets/skeleton.html`。单文件，CSS、时间线和柱状图的 JS 都写好了，把【】里的占位换成当天的内容，用不上的组件整块删掉。
- **语言和粒度细则**：`references/style.md`。

## 流程

### 1. 问清范围

先确认两件事，再动手：

- **哪一天**。按本机时区算。
- **哪个项目**。可以是目录名的一部分，比如 `my-app`；也可以是几个目录。

如果用户的消息里两样都说清楚了（例如「10 月 9 号 my-app 目录下的 session」），直接用，不要再问。

缺哪样就问哪样。有 AskUserQuestion 工具时用它问，选项里放上合理的默认值，例如「今天」和当前工作目录对应的项目。

### 2. 拉取当天的 session

```bash
python3 <skill 目录>/scripts/extract_day.py --date YYYY-MM-DD \
  --project <目录或 cwd 子串> --keyword <内容关键词> --out <scratchpad>/day
```

脚本会扫描那天所有项目目录下的 session，在 `index.md` 里分成三组：

- **matched**：项目目录名或者 session 的 cwd 命中 `--project`。
- **mentioned**：从别处启动（比如 `~/Codes`），但当天的对话和工具调用里多次提到 `--keyword`，可能也是在做这个项目。逐个打开看，是项目工作就算进来。
- **other**：只列标题，用来确认没有漏掉的。

matched 和 mentioned 两组，每个 session 会生成一份精简文本：只保留用户消息和 200 字以上的 AI 回复，子 agent 的对话已经去掉。

- 先读 `index.md`，再按需读 session 文件。文件大的话分段读，重点看用户消息和每轮最后的总结。
- `--keyword` 选项目的短名，比如项目目录叫 `my-app-workspace` 就用 `my-app`，这样能匹配到路径和对话里提到项目的地方。

**筛选规则**
- **同一个 session 可能有多个文件**：恢复或分叉后会这样，标题相同、时间重叠，合成一条工作线。
- **排除**：
  - 正在生成这份日报的 session 本身。通常是最新的那个、最后一条用户消息就是要日报的，标题多半带「日报」「例会」；
  - 跟项目本身无关的内容，比如另一个产品的 demo、闲聊；
  - 用户自己说「串台了」的那部分。
- **拿不准放不放的**：放到第 4 步的大纲里问用户。

### 3. 核对事实（按当天的工作类型来）

transcript 是当时的快照，状态可能已经变了。只核对当天工作里实际涉及的东西：

- **涉及 PR、提交、issue 时**：用 `gh pr view` / `gh issue view` / `git log` 查现在的状态。transcript 里写「已开 PR」，事后可能已经合了。
- **调研、设计、讨论类的工作**：没有 git 可查，就以产出的文档为准。看文件是否还在、最后修改时间、结论写在哪一节。也可以只按 transcript 写，标明这是当天的结论。
- **数字**（测试数、token、耗时、样本量）：照 transcript 原文写，不要四舍五入成「约几千」。

拿不到证据的就不写，或者写明「未验证」。不要为了核对去跑重的命令，也不要改任何东西。

### 4. 先对齐大纲（默认要做）

在回复里给出下面三样，然后停下来等用户确认：

1. **素材速览表**：时间（当地）/ 工作线 / 结果，一条工作线一行。
2. **5 段大纲**，每段 2 到 4 条要点：
   - 开场一句话
   - 做完了（可以分「主线」和「顺手修的问题」）
   - 进行中
   - 需要协调 / 风险
   - 明天
3. **需要用户拍板的问题**：只问会影响内容的，一般 3 到 5 个。比如某个 session 放不放、受众的技术背景、某件事算做完还是进行中、transcript 和实际状态对不上时报告里怎么写。

用户说「直接出」「不用对齐」时跳过这一步。用户在这一步给的反馈都要照做。

### 5. 写 HTML

- **视觉**：骨架本身已经带好视觉规范：暖白底、全文不用渐变、示意图用内联 SVG、数据图带结论标题。装了 `design-html` skill 的话，画示意图和数据图时可以参考它的细则。
- **不用做手机适配**：这份报告只在电脑上开会时看，不做 375px 手机检查和截图验收。
- **骨架**：从 `assets/skeleton.html` 复制一份开始写。它是自带 CSS 的单文件，不需要任何构建步骤。时间线的时间窗口和柱状图的刻度会根据数据自动计算，只改 `rows` 和 `bars` 两个数组即可。

**固定结构**
1. **标题**：`<项目>-每日例会-YYYY-MM-DD`。meta 行写「作者 · 日期（星期几）· 今天在 <项目> 上跑了 N 个工作 session」。星期几用 `python3 -c "import datetime;print('一二三四五六日'[datetime.date.fromisoformat('YYYY-MM-DD').weekday()])"` 算，不要自己推。
2. **开场一句话**：用 `.lead` 样式，说清今天的主线和它现在的状态。
3. **4 张数字卡**：选当天最能说明进展的数字。有 PR 和 issue 就写编号；调研类的一天，可以写产出了几份文档、定了几个决定、排除了几个方案。
4. **时间线**：HTML 甘特条，已完成用蓝色，进行中用橙色，时间都是当地时间。
5. **做完了：主线**：
   - 一段白话；
   - 一张机制示意图，画数据或流程真正怎么走；
   - 一条步骤条；
   - 若干「技术说明」块；
   - 如果产出了用户能看到的东西（报告、页面、接口），用一张表讲清它的结构；
   - 有数字就配数据图或表，最后放「验证」块。调研类工作把「验证」换成「依据」，写结论来自哪些资料或实验。
6. **做完了：顺手修的问题**：每项一个 `.item`，状态用 pill 标出来。白话写 1 到 2 句，下面接一个技术说明块。能用「以前 / 现在」讲清楚的，就做一个 `.ba` 对比卡。
7. **进行中**：3 条白话、一张任务状态表（任务 / 做什么 / 状态）、一个技术说明块。
8. **需要协调 / 风险**：只写我们这边的风险和待确认事项。同事负责的事、要转给同事的话，默认不写，除非用户要求。
9. **明天**：3 到 5 条具体动作。第二天是周末时改成「接下来」；这部分如果是你推断的，在回复里说明。

**写法**：严格按 `references/style.md`。核心有三条：
- 白话层能直接念出来，不出现内部代号；
- 技术说明层具体到模块名、根因、设计取舍和数字；
- 去掉 AI 腔。

写完在桌面宽度下自己通读一遍，检查三件事：示意图的线有没有压到节点和文字、表格有没有撑破版面、全文有没有出现 `gradient`。

### 6. 交付

- 文件名用 `<项目>-standup-YYYY-MM-DD.html`，存到用户能直接打开的位置，一般是当前工作目录下。在 git 仓库里，先用 `git check-ignore -q <路径>` 确认这个位置会被忽略；不会被忽略的话，换到已被忽略的目录，或者存到会话的 scratchpad，免得报告被误提交。
- 有 SendUserFile 工具时，用它把文件发给用户；没有就给出文件路径。不要只给服务器链接，读报告的人不一定连得上那台机器。
- 用户明确要局域网链接时，再跑 `bash <skill 目录>/scripts/publish.sh <report.html>`。它会把文件复制到 `~/standup/`，复用或新起一个静态服务，不会占用别人的端口。这个服务没有登录验证，能连到这台机器的人都能浏览 `~/standup/` 下所有的报告。机器有公网 IP 时，先告诉用户这一点。

### 7. 回复用户

回复要简短，包含：

- 文件；
- 覆盖了哪些工作线；有意没放进去的写明是哪些、为什么；
- 需要用户留意的事实出入，比如 transcript 里的说法跟现在查到的状态不一致；还有哪些内容是你推断出来的。

## 注意事项

- **只写 session 里真实发生、能核对的事。** 宁可写「未验证」，也不要补全没发生的结果。
- **transcript 里出现的账号、密码、key 一律不写进报告。**
- **不碰正在运行的服务。** 需要关掉某个服务时，按端口找到 pid 再关，不要按进程名模式去杀。

# design-html

产出一个独立的 `.html` 文件,讲清楚思路、取舍和理由,不是技术文档。内容怎么组织、分几节、画哪些图,由你按内容判断。本文件只规定**交付物要达到的质量**。

**怎么产出**:你只写 `design.src.html`(`<main>` 里面的内容:正文、架构图和数据图的数据块、其他手绘示意图),然后运行构建脚本生成 `design.html`。基础样式、架构图和数据图的绘制、截图都由脚本完成,不要自己写基础 CSS,也不要手算架构图和图表的坐标。

```bash
python3 <本 skill 目录>/scripts/build.py design.src.html --shot
```

## 1. 内容

- **大标题**(`<h1>`)是对文档主题的简洁陈述,用名词短语,不带口语、结论、情绪或设问。参考格式 `项目-主题-文档类型`。脚本用它生成 `<title>`。
  - ✅ `adrecta-eval-首跑结论`、`boban-审批流-重构方案`
  - ❌ `GLM 5.2 过了第一关,但这张卷子太简单`
  - 结论写在正文开头和每张数据图的标题里,不写进大标题。
- **多画图**。描述结构、流向、先后顺序、状态变化、前后对比时都用图,不写成大段文字。整体架构图是底线(用 `arch` 块,第 2 节)。每张图配一两句话说明看图重点:示意图写在图下方,数据图写成图上方的结论标题(第 3 节)。
- **有数字就用数据图或对比表**。方案之间比大小、随时间或规模变化、多方案多指标,都画出来(第 3 节),不写成段落里的一串数字。
- 不放代码片段(SQL/正则/schema/JSON)和过细的字段表,除非用户要。
- 文档里的中文（正文、图表标题、口径、标签）一律用全角标点：，。；：（）「」。数字里的千分位和小数点保持半角，如 `¥5,100`、`2.1%`。

## 2. 示意图(架构、流程、时序)

### 架构图:写 `arch` 数据块,交给脚本画

系统由哪些部件组成、各自跑在哪、谁调用谁,都算架构图(包括部署图、组件关系图)。你只需要声明分组、节点放在网格的哪一格、连线；节点尺寸、分组虚线框、正交走线、端口错开、交叉小弧、标签避让和手机版都由脚本处理:

```html
<script type="application/json" data-chart="arch">
{"caption": "界面和登录留在本机，CLI 在服务器上跑；模型请求从服务器直接出去。",
 "zones": [{"id": "pc", "name": "你的电脑", "tone": "violet"}, {"id": "srv", "name": "Linux 服务器", "tone": "green"}],
 "nodes": [
   {"id": "app", "name": "Claude Desktop", "sub": "界面 · 会话 · 登录", "zone": "pc", "at": [0, 0], "m": [0, 0]},
   {"id": "bridge", "name": "server --bridge", "sub": "stdio ↔ rpc.sock", "zone": "srv", "at": [1, 0], "m": [0, 1]},
   {"id": "cli", "name": "ccd-cli × N", "sub": "每个会话一个", "zone": "srv", "at": [1, 1], "m": [0, 2]},
   {"id": "api", "name": "api.anthropic.com", "sub": "模型推理", "at": [1, 2], "m": [0, 3]}],
 "edges": [{"from": "app", "to": "bridge", "label": "ssh", "both": true},
           {"from": "bridge", "to": "cli"}, {"from": "cli", "to": "api"}]}
</script>
```

字段说明见 `references/chart-spec.md`。**你要判断的**:

1. **摆位置**:`at` 是 `[列, 行]`。按请求的走向排,主链路尽量放在同一列或同一行;同一分组的节点占一块连续的矩形。空行、空列脚本会自动压掉
2. **分组表示运行位置或信任边界**(本机、服务器、云、第三方),画成虚线框,框名直接写在框上。节点颜色表示归属,默认跟所在分组走;外部服务、基础设施用 `gray`
3. **线默认用中性灰,表示谁调用谁**。只有在需要区分数据流的性质时(比如请求和答案、在线和离线)才用 `flow` 三色(第 2 节「颜色语义」);`dash` 只表示不一定发生的路径(异步、可选、降级)
4. **线上只写短标签**,比如协议、端口(`ssh`、`HTTPS`、`:443`);要解释的话写进 `caption`。`caption` 写看图重点
5. **手机版**:`m` 是手机版坐标。图在手机上会缩得太小时(一般是 2 列以上),给每个节点写 `m`,排成 2 列以内的纵向版本;不写时脚本把图改成横滑并警告
6. 构建报「穿过别的节点」时调整 `at`;报线重叠时用 `route` 给那条线换一种走法

### 其他示意图:手绘 SVG,视觉和架构图一致

流程、时序、状态变化、方案对比用内联 SVG 手绘,放在 `<figure class="diagram">` 里。节点、分组、线直接用架构图的 class:节点写成 `<g class="a-n t-green"><rect rx="6" …/><text class="t">标题</text><text class="s">副标题</text></g>`,分组框用 `<g class="a-z">`,线用 `<path class="a-e">`(虚线再加 `dash`)。图复杂到手绘保证不了下面的标准时,可以改用 drawio 导出 SVG 嵌入。最终稿不用 Mermaid。

下面的标准对手绘图都适用;`arch` 块里的走线规则由脚本保证,你只需要管「画机制」和颜色语义。

- **画机制,不画名字**。画出请求和数据真正走过的路径、跨过的边界。方案对比画同一张底图,高亮两个方案不同的那几条边,不要画成两排互不相连的方框。
- `<figcaption>` 写看图重点;`<svg>` 加 `role="img"` 和概括同一重点的 `aria-label`。节点按 8px 网格对齐,viewBox 内字号 ≥ 13。

**走线**
- 线不穿过任何节点卡片,也不压文字(文字周围 4px 内没有线)
- 跨区域连线用正交折线。不同路径的两条线,水平段 y 不重合、垂直段 x 不重合,不能只差几像素。同一条主链上首尾相接的几段线可以在一条直线上
- 多个同等地位的来源进同一个目标:先汇成一根干线,只留一个箭头头
- 线尽量不交叉,先调整节点位置。确实避不开时,交叉处让后画的那条线用半径 6px 的小弧跨过去,不要两条线直接十字相交
- 线上最多写协议、端口这类短标签,文字下垫底色,不压线。要解释的用编号圆圈,编号的说明写在图下的 `<figcaption>` 里,按编号顺序一行一条
- 虚线只表示「不一定发生」的路径,如降级、异步、可选步骤,并在图例里写明含义

**颜色语义**
- 一种颜色只表示一种含义。节点颜色表示归属(属于哪个分组、是不是外部服务),线的颜色表示数据流的性质,两者不混用
- 示意图里表达含义的每种颜色/线型,图例里都有;图例里没有的,图里不出现。节点颜色和所在分组一致时,框名已经说明了含义,不用进图例;节点白底、中性灰的线不算
- 节点色:`blue` `green` `orange` `violet` `gray`(class `t-<色>`),浅底 + 同色描边 + 深色字,一张图最多用 3 种
- 线默认中性灰 `var(--a-line)`。需要区分数据流时用下面三色。三色两两之间在色弱模拟和灰度下都能区分,不要换成别的颜色:

| 数据流 | 变量 | arch 块里写 |
|---|---|---|
| 主交互 / 发起动作 | `var(--flow-main)` 深蓝黑 | `"flow": "main"` |
| 输出 / 结论 | `var(--flow-out)` 正红 | `"flow": "out"` |
| 输入 / 素材流入 | `var(--flow-in)` 深紫 | `"flow": "in"` |

手绘时在 SVG 里写成 `style="stroke:var(--flow-main)"`。文字用 `var(--text)` / `var(--text-2)`。

**动画**(可选,只用于手绘图):箭头用 `stroke-dasharray` 做流动,节点错开淡入。`prefers-reduced-motion` 时关掉。

## 3. 数据图与对比表

数据图和对比表不手写,写成数据块交给脚本画:

```html
<script type="application/json" data-chart="bar">
{"title": "混合检索 v2 把召回率从 41% 提到 79%", "note": "召回率@10；500 条真实用户问题；细线为 95% 置信区间",
 "unit": "%", "items": [{"name": "BM25 v1", "value": 41, "ci": [37, 45]}, {"name": "混合 v2", "value": 79, "ci": [75, 83]}]}
</script>
```

五种块:`entities`(实体配色)、`stat`(数字卡)、`bar`、`line`、`table`。字段说明见 `references/chart-spec.md`,完整示例见 `references/chart-sample.src.html`。

脚本已经处理好的,不用再管:柱子和折线的尺寸与坐标、刻度取整、误差线、锁图标、线尾标签排序和避让、阈值标注、对比表推荐列移到第一列并加框、每行最优高亮、手机端布局(柱子超过 4 根时手机上自动改成横向,折线的日期标签自动减少)。

**你要判断的**

1. **先选形式,再看脚本能不能画**。不要为了用上脚本去改图的形式。

   | 要说的是 | 用 |
   |---|---|
   | 一两个关键数 | `stat` 数字卡 |
   | 几个方案或版本比大小 | `bar`,可分组 |
   | 几个方案在同一组类目上逐项对比(如 v3、v2 在每档攻击下的绕过率) | `bar` 成对横条:`categories` + `series` |
   | 随时间或规模的变化 | `line` |
   | 多方案 × 多指标 | `table` |
   | 单个方案在程度递进的类别上(弱 → 强) | `bar` + `"colors": "ramp"` |

   要比较两个方案时,把它们放进同一张图,不要拆成两张各画各的。红色阶只用于单个方案;比较多个方案时用各自的实体色。

   不用饼图、环形图、双 y 轴、雷达图、3D 图。数据装不进这五种格式时,照 `references/chart-sample.html` 手写那一张图,并遵守本节的规则。

2. **`title` 写结论句,`note` 写口径**。✅ `混合检索 v2 把召回率从 41% 提到 79%` ❌ `召回率对比`。口径写测的是什么、样本量、误差线含义、是否对数刻度、测试条件。
3. **在正文开头写一个 `entities` 块,给全文的实体定颜色**。同一实体全文同色:
   - 推荐方案或最新版用 `blue`,其他家族依次用 `green`、`orange`、`violet`
   - 单系列的图不画图例;成对横条由脚本在图顶自动加一行系列标注
   - 同家族的旧版用对应的 `-lt` 浅色版
   - 线上现状、对照组用 `gray`
   - 最多 4 个家族。实体更多时,把次要的合并成「其他」(`gray-lt`),或者拆成两张图
4. **区分 0 和无数据**:测了、结果是 0 写 `"value": 0`;没法测写 `"value": null`,原因写在 `sub`。
5. 预算、上限这类阈值用 line 的 `threshold`。对比表的每一行都给 `better`(`high`/`low`)或 `best`,推荐列标 `pick`。

## 4. 视觉:暖白底,克制

基础样式在 `assets/base.css`,脚本会原样内联,不要自己重写。确实需要少量额外样式时,在 `design.src.html` 里写一个 `<style>`,脚本会把它放在基础样式后面;颜色只用 base.css 里的变量。**全文不出现任何渐变**。

正文可以直接用这些 class:

| class | 用途 |
|---|---|
| `.meta` | h1 下面的灰色信息行(日期、范围) |
| `.lead` | 正文开头的结论段 |
| `.cards` > `.card` | 卡片网格,窄屏自动单列;卡片标题用 `<h4>` |
| `.two-col` | 两栏对照,窄屏上下堆叠 |
| `.callout` / `.callout.key` | 引用块 / 强调块 |
| `figure.diagram` | 手绘示意图容器 |
| `.tbl-wrap` > `table.tbl` | 普通表格(非对比表),外层可横滑 |
| `.scroll-x` | 宽示意图在手机上横滑 |

- 颜色只用来表达语义,不用来装饰;层次靠 1px 细线和留白来分,不用阴影
- 只做浅色主题。不用脉冲、hover 上浮这类装饰动效

## 5. 移动端

文档常被转发到飞书/微信,用手机打开。375px 宽度下必须可读,且页面整体不横向滚动。base.css 和图表已经处理好手机布局;你要注意的是手绘部分:

- `arch` 架构图写了 `m` 时脚本自动出桌面、手机两版;图宽、没写 `m` 时脚本把图包进横滑容器并警告
- 手绘示意图 SVG 在窄屏下文字会跟着缩小。横向铺开的宽图,再画一张纵向排布的版本给手机用:桌面版加 `class="only-desktop"`,手机版加 `class="only-mobile"`,两张内容一致。实在不好改纵向的,用 `<div class="scroll-x">` 包住并给 SVG 设 `min-width: 720px`
- 自己写的网格和两栏在窄屏下要能变成单列

## 6. 交付标准

- 运行 `python3 <本 skill 目录>/scripts/build.py design.src.html --shot`。它会生成 `design.html`,在同目录截出 `desktop.png`、`mobile.png`,并打印手机宽度检查结果 `sw=375 ✓`
  - 构建失败(退出码 1):按报错改 `design.src.html` 再跑。数值超出 `max`、负值、字段类型不对都会直接报错,不会画出错图
  - 退出码 2:构建成功,但手机上页面横向溢出,按提示找宽表格、宽图
  - 有 ⚠ 警告:逐条处理,尤其是未声明的实体、标不出最优值的行、架构图的线重叠和缺图例
  - 打印「跳过截图」(找不到 Chrome、测量失败或截图没写出来):改用浏览器工具的 375 手机视口检查,并确认 `document.documentElement.scrollWidth` 等于 375;都做不到就告诉用户手机端没检查
- **交付前必须亲眼看过两张截图**,对照第 1–5 节逐项检查,不过就改,改完重新构建。截图很长,按高度切成几块逐块看,重点找:文字压线、压柱、压节点,文字被截断,图没画全。改了三轮还有问题,就停下来告诉用户卡在哪里
- 交付物是 `design.html`,单文件,双击即可打开。`design.src.html` 留在同目录,方便以后修改;截图可以删掉
- 回复里用一两句话说明检查了什么、改了什么,不要只说"已生成"
